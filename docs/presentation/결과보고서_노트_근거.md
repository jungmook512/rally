## p.4 · s04 — 상지 재활 파트너 로봇 RALLY

기획서 1.1: 로봇은 테이블 반대편에서 공·패드·컵·막대 같은 물체를 통해서만 환자와 상호작용한다(로봇이 환자를 잡거나 미는 동작은 없음). 상지 재활 훈련의 상대 역할을 하고, 동작과 힘을 측정·기록한다. 훈련 모드 1·5 확정, 모드 3 은 챌린지(Day 6). 그림: 작업대 배치 개념도(실제 치수와 다를 수 있음) — 공 거치대에서 공 4개 자동 공급(모드 1), 가이드 레인 2개는 환자 손 위치로 선택, 막대 집기 구역(모드 5), 패드 거치대·벨크로 공 박스(모드 3), 보라색 선은 로봇 이동 한계.

## p.5 · s05 — 선정 배경 — 상지 재활 훈련의 현실

환자: 상지 기능 회복에는 과제 반복이 핵심이다(French 2016 Cochrane, 33편 1,853명 — 반복 과제 훈련이 상지 기능을 개선, 6개월 유지). 그런데 실제 PT·OT 세션을 관찰하면 상지 과제 반복은 세션당 평균 32회였다(Lang 2009, 312회 관찰). 1시간에 300회 이상도 가능하다는 개념 증명이 있다(Birkenmeier 2010) — 300회는 공식 권고량이 아니라 실현 가능한 양. 실제 물체가 있을 때 뻗기 동작이 더 빠르고 매끄럽다(Wu 2000, 소규모).

치료사: 환자 한 명을 붙잡고 공을 주고받는다 — 반복 상대가 늘 사람이어야 한다. 보상 동작은 주로 눈으로 보고 질적으로 판단하며, 같은 영상을 본 치료사 22명의 일치도가 항목에 따라 낮았다(Sauerzopf 2024 JNER — 매끄러움 ICC 0.49, 관절 협응 0.40). 단, FMA 같은 표준 척도 자체는 신뢰도가 높다 — "치료사 평가가 부정확하다"고 말하지 않는다. 표준 척도는 운동 부분만 20~30분이라 주기 평가용이고 세션 안 변화는 담지 못한다.

기존 재활 로봇: 상용 15종(InMotion, Armeo, ReoGo, H-Man, Tyromotion, 네오펙트 등)은 팔을 끌거나 보조하며 화면 게임을 시킨다(p.6). 궤적형 로봇(MIT-Manus) 훈련은 일반 치료보다 상지 기능을 더 개선하지 못했다(RATULS, Lancet 2019, 770명). 보상 감지는 ArmeoSenso(착용 IMU)·MindMotion PRO(카메라) 정도이고, 피로 신호로 휴식을 제안하는 상용 기능은 찾지 못했다.

## p.6 · s06 — 기존 재활 로봇은 팔을 움직이는 기계 — RALLY 는 주고받는 상대

핵심 메시지: 기존 상지 재활 로봇은 환자 팔을 정해진 궤적으로 끌거나 보조하면서 화면 게임을 시키는 '운동 기계'다. RALLY 는 실제 공·막대를 주고받는 '훈련 상대'다.

엔드이펙터형: InMotion(Bionik, 국내 큐렉소 유통) · ReoGo · H-Man · Burt — 손잡이 + 화면, assist-as-needed. 외골격·센서형: ArmeoPower/Spring/Senso(Hocoma) — ArmeoSenso 는 착용 IMU 로 몸통 보상 감지가 핵심 기능. 장갑·테이블형: 네오펙트 스마트 보드·글러브(AI 난이도 조절, 몸통은 자세 고정으로 통제), Gloreha, Tyromotion Myro(실제 물체를 쥐고 터치 화면). 카메라 기반 VR 인 MindMotion PRO 도 실시간 보상 피드백을 한다. 소셜 로봇: Pepper(Feingold-Polak 2021 JNER, 2024 TNSRE) — 실제 물체 과제를 말로 지시, 로봇이 물체를 건네지는 않음.

협동로봇 재활 리뷰(Raji 2025, BioMed Eng OnLine, 33편): UR5·YuMi·KUKA·Franka 등, 대부분 손목에 붙여 보조·저항, 아직 초기 단계.

피로 신호로 휴식을 제안하는 상용 기능은 찾지 못함(연구는 대부분 EMG 기반·건강인 대상).

대표 장비: 엔드이펙터형 InMotion · ReoGo · H-Man · Burt / 외골격·센서형 Armeo Power · Spring · Senso / 장갑·테이블형 네오펙트 · Gloreha · Myro / 소셜 로봇 Pepper(TNSRE 2024). 과제 범위: 엔드이펙터 팔 뻗기 위주, 외골격 어깨~손, 장갑 손·손목, RALLY 뻗기·손목 회전·쥐기·협응.

조사 범위: 상용 상지 재활 장비 15종(제조사 자료) + 협동로봇 재활 리뷰 33편. RALLY 의 임상 효과는 검증하지 않음.

표현 주의: "세계 최초" 금지. "조사한 범위에서 찾지 못했다"로만. 표의 '없음'은 찾지 못했다는 뜻. 임상 효과는 검증 전.

## p.7 · s07 — 기획 의도 — 차별화 포인트 4가지

① 주고받는 훈련 상대(메인): 모드 1 은 환자 손에 가까운 레인을 골라 공을 굴리고, 모드 5 는 돌려받을 때 손목을 막대 각도에 맞추고, 모드 3 은 던진 공의 교차점을 예측해 받으러 간다. 조사한 상용 15종 중 로봇이 실제 물체를 환자와 주고받는 방식은 찾지 못했다. 실제 물체가 있으면 뻗기가 더 자연스럽다는 보고(Wu 2000)와 과제 반복 훈련의 효과(Cochrane 2016)에 근거한 설계.

② 무리하지 않게: 보상 동작 감지는 규칙 — body_pose 가 팔을 뻗는 동안 몸통 기울임·어깨 들림을 평소 자세 대비 각도 임계로 판정 → 바로 음성 코칭. 보상 동작 반복(최근 5회 중 3회)·성공률 하락·느려짐이 쌓이면 LLM 이 계속/휴식 제안을 정한다(환자가 수락해야 휴식). 「힘들어」는 묻지 않고 휴식. 난이도는 환자가 요청할 때만 바꾼다. 감지 자체는 연구가 많다(Kinect·MediaPipe) — "이미 연구된 감지를 로봇 훈련 루프에 묶었다". 어깨 들림은 카메라로 잡기 어렵다는 보고가 있어(Zhi 2017, Unger 2025) 개인 기준선 대비 보조 신호로 쓴다.

③ 로봇 하나로 여러 과제: 같은 협동로봇이 물체만 바꿔 모드 1·5·3 을 음성으로 전환. 기존 장비는 대부분 한 부위 특화.

④ 같은 기준으로 기록: 로봇 장비는 대부분 기록 기능이 있으므로 비교 대상은 치료사 1:1. 보상 동작은 눈으로 보고 판단하며 항목에 따라 평가자 간 일치도가 낮다(Sauerzopf 2024). 표준 척도(FMA)는 신뢰도가 높으니 "치료사 평가가 부정확하다"고 말하지 않는다 — RALLY 는 척도를 대신하지 않고 보완한다.

이전 판의 '규칙 우선·LLM 격리', '영상 외부 미전송'은 차별점이 아니라 설계 원칙이라 p.8 핵심 설계 결정에서 다룬다.

## p.9 · s09 — 기대 효과 — 환자 · 치료사 · 운영

p.7 차별점 4개가 누구에게 어떤 효과로 이어지는지 정리한 페이지. 효과를 수치로 단정하지 않는다(임상 검증 없음). 환자: ① 실제 물체 과제(모드 1 = 앞으로 뻗기 · 서서 몸통 조절, 모드 5 = 쥐기 · 놓기 · 손목 돌리기(회내 · 회외), 모드 3 = 어깨 큰 동작 · 타이밍, 근거 가장 약함, 챌린지). 로봇이 손 위치에 맞춰 레인을 고르고 막대 각도를 맞추고 공을 받으러 간다. ② 보상 동작이 보이면 바로 「몸은 세우고 팔로만 뻗어 보세요」 같은 코칭, 신호가 쌓이면 휴식 제안(수락해야 휴식), 「힘들어」는 바로 휴식. 치료사: 반복 상대 역할을 로봇이 맡는다. 보상 동작은 임상에서 주로 눈으로 판단하고 평가자 간 일치도가 항목에 따라 낮다(Sauerzopf 2024) — RALLY 는 같은 기준의 기록을 남겨 비교할 수 있게 한다(대신하지 않는다). 표준 척도(FMA 등)는 주기 평가용이라, 그 사이 세션 추이를 리포트로 채운다. 운영: 범용 협동로봇 1대에 물체만 바꿔 여러 과제. 환자는 음성(「랠리야 → 시작」, 모드 전환, 「힘들어」, 재개, 「어렵게 · 쉽게」, 「여기까지 하자」), 치료사는 대시보드(재개 · 모드 전환 · 종료)로 세션을 운영 — 둘 다 로봇에 직접 명령하지 않고 brain 이 안전 · 휴식 · 손 상태를 확인한 뒤 시도 경계에서 실행. 정지는 환자 비상어 「그만 · 멈춰」, 하드웨어 버튼, 터미널 estop 누구나 가능하고, STOP 해제는 사람이 reset_safety 로만(자동 해제 없음). 영상 원칙은 p.8. 한계: 임상 검증 없음, 보상 동작 · 피로 신호는 보조 신호(어깨 들림은 카메라로 잡기 어렵다는 보고 — Zhi 2017, Unger 2025), 서서 하는 훈련이라 경증~중등도 한정, 반복 횟수(모드당 4~5회).

## p.11 · s11 — RALLY 시스템 아키텍처

GPU 가 한 대라 카메라→인식→로봇 경로를 한 PC 에(지연·대역). 판단·DB 는 두산 SDK 없이 서버 PC 에(10/6). 음성(스피커·마이크·TTS·의도)은 10/14 부터 서버 PC. pc1 네이티브: 두산 드라이버·force_publisher·gripper·safety_monitor(100 Hz)·skill_server·camera_tf. pc2 컨테이너: segmenter·flight_predictor·hand/body_pose. pc3: context_builder 5 Hz·bt_runner·llm_advisor(휴식 판단·리포트), recorder(db)·redis·dashboard·intent/tts. 두 PC 는 Fast DDS Discovery Server(서버 PC)로 한 ROS. 전체 배선도는 부록 A-4. 그림 흐름: 손목 RealSense(물체·손 3D, 60 Hz)·측면 RealSense(날아오는 공·몸 자세) → 인식(YOLO·MediaPipe·EKF) → 인식 결과를 서버 판단(brain, 행동 트리 규칙 먼저 · LLM 휴식 제안)으로 → 스킬 명령이 로봇 제어(스킬 액션 서버, amovej 요격, 출발은 규칙 / PPO 선택)로. 안전 감시 100 Hz 가 감속·정지, 음성 비상어와 대시보드 비상 정지는 안전 감시로 바로. 외부 LLM API 에는 허용된 수치만, 영상은 PC 밖으로 나가지 않음.

## p.27 · s27 — ④ 모드 3 ① 인식 — 날아가는 공을 놓치지 않고 3D 로

[대본 · 약 1분] 모드 3은 던진 공을 패드로 받는 챌린지입니다. 여기에는 세 가지 관문이 있습니다. 공을 제대로 보는가, 어디로 올지 정확히 맞히는가, 그리고 시간 안에 도착하는가입니다. 이 장은 첫 번째, 인식입니다.

공은 손을 떠나 약 0.75초 만에 날아옵니다. 저희는 로봇 손목 카메라와 측면 카메라 두 대로 이 공을 초당 60장씩 찾습니다. 사진이 16.7 ms마다 한 장씩 들어오니, 두 카메라 사진을 합쳐 16.7 ms 안에 처리해야 합니다. 이보다 늦으면 사진이 밀려서 건너뛰게 됩니다. 실제로 초당 30장으로 떨어져, 공을 볼 기회가 절반으로 줄어든 적이 있습니다. 그런데 일반 PyTorch로는 느린 순간이 17.2 ms라 예산을 넘었습니다. 그래서 TensorRT로 바꿔 15.5 ms로 줄였습니다.

두 번째는 3D 위치입니다. 처음에는 두 카메라 사진을 같은 시각끼리 짝지어 삼각측량했습니다. 그런데 문제가 두 가지 있었습니다. 처리가 초당 30장으로 떨어지면 짝이 맞지 않아 예측을 아예 못 내는 투구가 있었고, 공이 아직 손에 있던 장면이 섞여 초반 예측이 아래로 쏠렸습니다. 그래서 짝짓기를 버리고 카메라마다 찍힌 시각 그대로를 궤적에 맞추는 방식으로 바꿨고, 손에 있던 장면은 잘라냈습니다. 그 결과 빠른 투구의 예측 오차가 10.6 cm에서 2.8 cm로 줄었습니다. 이 과정은 뒤의 트러블슈팅 첫 번째에서 자세히 말씀드리겠습니다.



[근거] 모드 3 챌린지 세 가지: ① 인식이 되는가(이 장) ② 예측이 정밀한가(다음 장, EKF) ③ 시간 안에 도착하는가.

## p.28 · s27c — ④ 모드 3 ② 예측 — 확장 칼만 필터(EKF)로 도착점을 정밀하게

KF 가 아니라 EKF 인 이유(질문 대비): 공기 저항 −k|v|v 가 속도 제곱에 비례하는 비선형이고, rays 관측(3D → 픽셀 투영)도 비선형이라 지금 추정값 근처에서 직선 근사(야코비안)하는 확장 칼만 필터를 씀. 보정하는 것 = 공의 상태 추정(3D 위치 · 속도 6개)과 그 불확실성. 물리 식(중력, 공기 저항 계수 k)은 고정. 새 관측마다 ① 예측: 지금 상태를 중력 + 공기 저항 식(RK4)으로 다음 관측 시각까지 굴림 ② 관측: 카메라 픽셀(rays) ③ 보정: 예측과 관측의 차이를 칼만 이득(지금 추정을 얼마나 믿나 vs 관측을 얼마나 믿나)만큼 반영 ④ 고쳐진 상태로 45° 패드 평면까지 적분해 교차점 · 시각 · 흔들림(표준편차)을 60 Hz 로 발행. 처음엔 속도를 잘 모르다가(첫 두 관측 차분 + 큰 초기 공분산) 관측이 쌓일수록 정확해짐 — 0.16 s 3.9 cm, 0.20 s 2.5 cm(중앙값, bag), 90 % 15 cm.

KF vs EKF: KF 는 움직임 · 관측 식이 선형일 때만. 중력만이면 선형이라 KF 로 충분하지만, 공기 저항 −k|v|v 는 속력 제곱에 비례하는 비선형이고 rays 관측(투영)도 비선형 → 매 단계 야코비안(수치 미분)으로 직선 근사하는 확장 칼만 필터. UKF · 파티클 필터도 가능하지만 60 Hz 에 더 무겁고, 보정 간격 약 17 ms 로 짧아 직선 근사 오차가 작아 EKF 로 충분.

공기 저항: v̇ = g − k‖v‖v, k ≈ 0.073~0.075 /m — 실제 투구 궤적(번들 조정, 10/10 투구 23회)으로 추정. 공 크기 · 무게로 계산한 0.013~0.018 보다 약 5배라 의문은 남지만 실제 궤적과 맞음. 공기 저항을 빼면 예측 오차가 약 40 cm(MODE3_OVERVIEW 4.3 — 3.9 cm 와 같은 조건인지는 미확인).

잡음 · 오검출: 측정 잡음 1.5 cm · 픽셀 3 px, 마할라노비스 거리 99.9 % 밖의 관측은 버림(한 카메라 오검출). 로봇은 흔들림 ≤ 13 cm · 관측 ≥ 4 일 때만 출발(품질 게이트). 그림은 설명용 모식도, 패드 면은 위로 45°(법선이 투구자 쪽 위).

## p.33 · s30b — ⑦ 인식 ② 사람 — MediaPipe 로 손 · 몸, 보상 동작

화면에서 뺀 내용 — 쓰는 곳: 손은 모드 1 레인 선택 · 받기 확인 · 회수 전 손 이탈, 안전 감시 손 ↔ 로봇 거리, 모드 5 잡는 순간 손목 각도 기록. 몸은 보상 동작 → 음성 코칭, 최근 5회 중 3회면 휴식 판단 신호. 측면 카메라를 쓰는 이유: 손목 카메라는 손만 보이고 몸 전체는 옆에서 1 m 이상 떨어져야 잡힌다. 보상 동작은 팔 기능 회복을 방해할 수 있어 치료사가 교정하는 부분(일반 설명, 근거 논문 미확인). 몸(body_pose): 측면 RealSense(eye-to-hand) 영상 → Pose 33점(pose_world_landmarks, 깊이 없이 MediaPipe 3D) → 몸통 기울임 · 어깨 들림 · 팔꿈치 펴짐. 처음 30프레임(약 2 s)을 평소 자세 기준으로 두고, 팔꿈치가 140° 이상 펴진(뻗는) 동안만, 기준 대비 몸통 기울임 20° 또는 어깨 들림 20° 이상이 5프레임(약 0.3 s) 이어지면 보상 동작(trunk_lean / shoulder_hike). 임계는 10/8 선 자세 시험에서 그냥 뻗어도 오탐이 나서 15° → 20° 로 올림. 보상 동작이 보이면 바로 음성 코칭, 최근 5회 중 3회면 휴식 판단 신호.

## p.34 · s31 — ⑧ 판단 — 규칙이 먼저, 신호만으로 단정 못 할 때 LLM

역할 나눔: 보상 동작 감지는 LLM 이 아니라 규칙이다 — body_pose 가 팔을 뻗는 동안 몸통 기울임·어깨 들림을 평소 자세(기준) 대비 각도 임계로 판정한다. LLM 은 그렇게 켜진 신호(보상 동작 반복·성공률 하락·느려짐)가 피로 때문인지 최근 기록과 함께 보고 「계속할지, 휴식을 제안할지」만 정한다. 왜 LLM 인가: 신호는 피로의 간접 증거라 같은 신호도 상황마다 뜻이 다르다 — 성공률 하락은 방금 난이도를 올려서, 느려짐은 신중하게 하느라, 보상 동작은 원래 습관일 수도 있다. 「신호 켜짐 → 무조건 휴식」 규칙은 과하고, 무시하면 진짜 피로를 놓친다. 단, LLM 이 규칙보다 낫다는 검증은 하지 않았다(설계 의도). rule_layer.decide 순서(코드 고정): 안전 STOP → 대기 / 음성 「힘들어」 → 묻지 않고 휴식(현재 시도 마친 뒤) / 「어렵게 · 쉽게」 / 3연속 성공 → 어렵게 / 2연속 실패 → 쉽게 / 휴식 신호 ≥ llm_signal_count → LLM / 그 외 계속. 휴식 신호 3개: 보상 동작 반복(세션 전체 최근 5회 중 3회, 10/15 #217 모드 무관), 성공률 40 % 이하(모드별 최소 3회), 직전 시도가 앞선 평균의 1.5배 이상 느림. 시연(10/15)은 신호 1개면 LLM(#219). LLM 호출: llm.yaml 화이트리스트 수치(모드·시도·성공·오차·시간)와 신호 불리언만, 답은 continue/suggest_rest 둘 중 하나(pydantic), 비동기 작업자 1, 3 s 타임아웃 → 규칙 폴백. STOP·취소·모드·난이도 변경이 생기면 답 폐기. 제안은 TTS 「혹시 피곤하진 않으세요? 조금 쉬었다 할까요?」 + 대시보드 20 초 카드, 수락해야 휴식. 조건이 쌓이는 과정은 대시보드 「휴식 제안 조건」 패널(#213).

## p.50 · s48 — 조정묵 휴식 제안 — LLM 은 「쉬자고 물어볼까」 하나만 고른다

화면 정리(10/16): 예시 값(모드 5 등)은 오해를 만들어 뺐다 — 실제로는 그때 훈련 중인 모드의 최근 시도가 들어간다. 시연 조건은 보상 동작 3회(세션 전체 최근 5회 중 3회) 하나만으로 LLM 판단(#219). LLM 을 쓰는 곳은 셋: 휴식 판단(이 페이지) · 세션 리포트 · 음성 의도 분류. LLM 호출 흐름(rest_advisor.py · prompts/rest_decision.md · rule_layer.py): 시도가 끝날 때마다 규칙이 위에서부터 — 1 안전 STOP → wait(코드 고정), 2 「힘들어」 → suggest_rest, 3 어렵게/쉽게, 4 연속 성공 → harder, 5 연속 실패 → easier, 6 애매한 신호가 llm_signal_count 개 이상 → ask_llm, 7 그 외 continue. 보내는 것(llm.yaml rest_send_fields · rest_send_signals, 코드에서도 다시 제한): 같은 모드 최근 최대 5회의 mode · trial_index · success · error_mm · duration_s 와 신호 compensation · success_drop · slowing 참거짓. 모드 1 은 success · success_drop 을 보내지 않는다(받기 후보는 실제로 잡았다는 증거 아님, #126). 받는 것: gpt-4o function calling, 스키마 enum continue / suggest_rest 하나, pydantic extra=forbid. 3 s 넘거나 오류·형식 오류 → continue. 한 번에 요청 하나(큐 없음). suggest_rest → 고정 문구 TTS + 대시보드 제안 카드(20 초 수락/거절), 수락하면 일시정지. 화면 예시(모드 5 · 보상 동작 참)는 설명용. 시연 조건 10/15 조정묵 결정(#219): llm_signal_count 2 → 1, 보상 동작은 세션 전체 최근 5회 중 3회(#217). 1.832 s 는 #103 gpt-4o 휴식 판단 응답. 실세션 휴식 제안 1회(신호 → 요청 → 응답 → 카드 → 수락)는 보강 예정, 임상적으로 맞았는지는 재지 않는다. 세션 리포트: 세션이 끝난 뒤 수치 요약 + Graph RAG(비슷한 과거 시도) → LLM 해석 글 → sessions.report_md, 해석 3.5 s, 제어와 무관. 음성 의도: 「랠리야」 뒤 Whisper → gpt-4o function calling 으로 시작 · 다음 · 힘들어 · 어렵게 · 쉽게 · 모드 분류. 이전 노트: 판단 5층(INTELLIGENCE.md): 규칙 레이어 → 온톨로지·지식 그래프 → Graph RAG(pgvector 유사 시도) → LLM 휴식 판단 → 세션 리포트. 애매한 신호: 보상 동작 반복(세션 전체 최근 5회 중 3회, #217) · 성공률 40 % 이하(최소 3회) · 1.5배 느려짐. LLM 엔 llm.yaml 화이트리스트 수치만, 답은 continue/suggest_rest, 3 s → 규칙 폴백. 트러블: ask_llm 로그만 → 비동기 연결(#103). 모드 1 받기 후보는 접촉 증거 아님 → 성공률 안 보냄(#126).
