# RALLY 판단 구조 — 전문가 시스템과 무엇이 다른가

작성: 조정묵 (지능·인프라 담당) · 2026-10-12
대상: 이 프로젝트의 "환자 상태 판단" 구조를 처음 보는 사람 (팀 밖 리뷰어, 포트폴리오 독자)

## 한 줄 요약

**안전과 제어는 규칙(전문가 시스템)으로 예측 가능하게 두고, 규칙으로 정하기 애매한 판단에만 과거 유사 기록 검색(Graph RAG)과 LLM을 붙인 하이브리드 구조다.** LLM의 출력은 정해진 선택지 중 하나로 제한하며, 실패하면 규칙으로 돌아간다.

"전문가 시스템이 아니다"라고 말하면 틀리다. 바닥은 일부러 전문가 시스템으로 만들었고, 그 위에 데이터와 LLM을 얹었다.

## 1. 전문가 시스템이란

- 전문가가 "만약 A면 B 해라" 규칙을 지식 베이스에 적어 두고, 추론 엔진이 그 규칙대로만 판단한다.
- 장점: 예측 가능하고, 왜 그렇게 판단했는지 설명하기 쉽고, 검증할 수 있다.
- 단점: 적어 두지 않은 상황을 다루지 못한다. 기록이 쌓여도 판단이 바뀌지 않는다.

## 2. RALLY의 판단은 다섯 층

시도가 하나 끝날 때마다 아래 순서로 판단한다 (`rally_brain/rule_layer.py` `decide`).

```
시도 결과 + 상황판(손·몸·안전·음성)
  │
  ├─ 1. 규칙 레이어 ── 안전 정지 → 대기 / "힘들어요" → 휴식 / 3연속 성공 → 어렵게 / 2연속 실패 → 쉽게
  │      (행동은 온톨로지 그래프에서 찾는다: 계기 —triggers→ 행동)
  │
  ├─ 2. 애매한 신호 2개 이상 (보상 동작 · 성공률 하락 · 시도 시간 증가)
  │      └─ 3. Graph RAG: 비슷한 과거 시도 → 그때의 보상 동작 → 피로 신호 집계
  │         └─ 4. LLM 휴식 판단: "계속" 또는 "휴식 제안" 둘 중 하나 (3 s, 검증, 실패 시 계속)
  │                └─ 휴식 제안은 대시보드에서 사람이 수락해야 적용
  │
  └─ 그 밖 → 계속 (모르면 바꾸지 않는다)

세션 끝 → 5. 세션 리포트: 수치 요약 + 지식 그래프 근거 표 + LLM 해석
```

| 층 | 하는 일 | 전문가 시스템과의 관계 | 코드 |
|---|---|---|---|
| 1. 규칙 레이어 | 안전·음성·연속 성공/실패에 따른 행동 | **전문가 시스템과 같다 (의도).** 안전과 제어는 예측 가능해야 한다 | `rule_layer.py` |
| 2. 온톨로지 + 지식 그래프 | 모드·보상 동작·피로 신호·행동 사이의 관계(RDF/JSON-LD)와, 시도마다 쌓이는 기록(세션 → 시도 → 모드, 시도 → 관찰된 보상 동작)을 한 그래프로 | 지식 베이스와 비슷하다. 다른 점: 고정된 규칙 목록이 아니라 **실제 기록이 계속 연결되는 그래프**이고, 규칙 레이어도 행동을 이 그래프에서 찾는다 | `knowledge/ontology.jsonld`, `rally_db/schema_004_graph.sql` |
| 3. Graph RAG | 지금 시도와 특징이 비슷한 과거 시도(pgvector)를 찾고, 그래프를 따라가 "보상 동작이 있을 때/없을 때 성공률" 같은 근거를 집계 | **전문가 시스템에 없다.** 근거가 사람이 적은 규칙이 아니라 쌓인 데이터에서 나오고, 기록이 늘면 근거가 달라진다 | `graph_rag.py` |
| 4. LLM 판단 | 규칙으로 정할 수 없는 신호 조합에서 휴식 제안 여부만 선택 | **전문가 시스템에 없다.** 일일이 규칙으로 적을 수 없는 조합을 다룬다 | `rest_advisor.py` |
| 5. 세션 리포트 | 숫자와 그래프 근거를 치료사·보호자가 읽는 문장으로 | 전문가 시스템의 설명은 "어떤 규칙이 발동했다" 수준이다 | `session_report.py` |

## 3. 왜 LLM을 정해진 선택지로만 쓰나 (팀 결정 #78, 2026-10-08)

1. **숫자 조절은 규칙이 더 잘한다.** 모드 1 밀기 속도를 LLM이 제안하게 했었는데, 물리식 레시피(정지 거리 = v²/2a + d0)가 이미 오차 15 mm 안으로 맞췄다. LLM은 3 s 지연이 붙고 같은 입력에도 답이 흔들려, 정직하게 비교하면 규칙에 진다. → 숫자는 레시피·규칙, LLM은 애매한 판단과 설명.
2. **로봇이 사람 바로 앞에서 움직인다.** LLM은 그럴듯하지만 틀린 답(환각)을 낼 수 있다. 선택지를 둘로 묶으면 최악의 경우에도 그 둘 중 하나이고, 휴식 제안도 사람이 수락해야 적용된다. LLM 출력은 로봇에 직접 가지 않는다.
3. **검증할 수 있다.** 정해진 선택지는 코드로 검사한다 (pydantic 스키마, 허용 목록, 범위 제한). 자유 답변은 맞는지 코드로 판단할 수 없다.
4. **실패해도 멈추지 않는다.** 키 한도 초과·네트워크 끊김·시간 초과면 "계속"으로 돌아가 세션이 그대로 진행된다 (실제로 개발 중 RateLimitError를 겪었다).

LLM에는 `llm.yaml` 허용 목록의 **집계 숫자만** 보낸다. 세션·시도 ID, 날짜, 자유 메모, 영상, 좌표열은 보내지 않으며 테스트로 검사한다.

**대가:** 유연성을 포기하고 예측 가능성과 안전을 택했다. 그래서 다음 절의 한계가 생긴다.

## 4. 한계 (정직하게)

- **정해 두지 않은 상황은 판단하지 못한다.** 규칙에도 애매한 신호에도 걸리지 않으면 "계속"이다. 모르면 바꾸지 않는 쪽이 안전하다는 의도된 기본값이다.
- **스스로 학습하지 않는다.** 모델을 훈련하거나 규칙을 자동으로 바꾸지 않는다. 난이도 조절은 고정 레시피다. 정확한 표현은 "기록이 쌓이면 판단 근거(Graph RAG 집계)가 달라진다"까지다.
- **"보상 동작 → 피로" 연결은 임상 근거가 약하다.** 기획 단계의 가정이며 온톨로지에 `evidence: weak`로 표시했다. LLM 프롬프트에서도 단정하지 않게 막았다.
- **기록이 적으면 Graph RAG는 거의 비어 있다.** 비슷한 과거 시도가 3개 미만이면 근거를 보내지 않는다.

## 5. 확장 방향 — 정해 두지 않은 상황을 다루는 기술

| 기술 | 원리 | 이 프로젝트에서 |
|---|---|---|
| 이상 탐지 | 이 환자의 평소 범위(시도 시간·힘·손목 각도)를 기록에서 배우고 벗어나면 "평소와 다름" | **가장 현실적인 다음 단계.** 데이터가 이미 쌓이고, 결과를 "운영자 확인 요청"으로만 쓰면 로봇 제어·안전 경로를 건드리지 않는다 |
| 사례 기반 추론 | 비슷한 과거 상황에서 무엇을 했고 결과가 어땠는지로 판단 | 절반은 있다 (Graph RAG가 비슷한 시도 검색까지). "그때 쉬었더니 좋아졌다"처럼 행동 → 결과까지 그래프에 이으면 완성 |
| LLM 범위 확대 | 상황 전체를 LLM에 주고 판단 | 기술적으로 쉽지만 검증이 어렵고 #78 원칙과 충돌. 넓힌다면 로봇을 움직이지 않는 출력(알림·설명)부터 |
| 분류기 학습 | "피로함/괜찮음" 정답 데이터로 학습 | 라벨 데이터가 없어 현재 불가 |
| 강화학습 | 결과를 보며 정책 학습 | 많은 시도와 환자 대상 시행착오가 필요. 모드 3 요격은 시뮬레이션에서 검토 중 |
